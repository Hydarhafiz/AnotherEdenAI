## Warnings

### WR-01: `_extract_json` greedy brace regex captures outermost object only — nested-fence fallback is not greedy

**File:** `src/workflow/nodes/format.py:76`
**Issue:** Attempt 3 (the `r"\{.*\}"` brace match with `re.DOTALL`) uses a greedy `.*` match, which correctly captures the outermost `{...}` block. However, attempt 2 (the markdown-fence regex on line 68) uses `r"```(?:json)?\s*(\{.*?\})\s*```"` with a **non-greedy** `.*?` on the inner group. A multi-key JSON object that spans many lines (e.g., the full team structure with nested lists) may be truncated by the non-greedy match: the inner `.*?` stops at the first `}` it finds inside the fence, which is often the closing brace of the first `CharacterSlot`, not the outer object. This means the fence-extraction path silently produces partial JSON, which then fails `json.loads`, causing the whole parse to fall through to attempt 3 — correct but unintentionally so, and fragile if attempt 3 is later removed.

**Fix:**
```python
# Line 68 — change .*? to .* for the inner JSON group (DOTALL already set)
fence_match = re.search(r"```(?:json)?\s*(\{.*\})\s*```", text, re.DOTALL)
```

### WR-02: `analyze_node` injects raw `db_results` list into the prompt without size guard

**File:** `src/workflow/nodes/analyze.py:69`
**Issue:** `db_results` is stringified via `f"Database results:\n{db_results}"`. The list is passed as-is with Python's default `str()` representation (not JSON). For large rosters or broad Cypher queries, `db_results` could contain hundreds of records, potentially exceeding the model's context window and causing a truncation error or an unexpected API error with no fallback. Additionally, using Python's default list stringification rather than `json.dumps` produces a less predictable format for the LLM to parse (single quotes, Python `None` instead of `null`, etc.).

**Fix:**
```python
import json

# Replace line 69
human_content = (
    f"User query: {user_query}\n"
    f"Player roster: {roster_str}\n"
    f"Traversal strategy: {plan_strategy}\n"
    f"Database results:\n{json.dumps(db_results[:50], indent=2)}"  # cap at 50 records
)
```

### WR-03: `format_node` error path is gated on BOTH `retry_count >= 3` AND empty `db_results` — a non-empty `db_results` with exhausted retries bypasses the error path silently

**File:** `src/workflow/nodes/format.py:109`
**Issue:** The error path condition is `retry_count >= 3 and not db_results`. If the graph ever reaches `format_node` with `retry_count >= 3` but a non-empty `db_results` (e.g., the last retry produced results), `format_node` proceeds to parse `analysis_result`. But `analysis_result` may be empty string `""` (never written by ANALYZE on that path), causing `_extract_json("")` to raise `ValueError`, which is caught on line 126 and returns the generic malformed-team error. This is a silent logic error: the error message "LLM returned malformed team structure — retry or check model" is misleading when the real cause is an empty `analysis_result`.

The `route_after_validate` function (in `graph.py`) routes to `format` only when `db_results` is empty at `retry_count >= 3`, so in normal graph traversal this cannot trigger. But the condition in `format_node` does not match the router's intent precisely, creating a latent divergence bug if routing logic ever changes.

**Fix:**
```python
# More explicit error path: match the router's intent precisely
if retry_count >= 3 and not db_results:
    ...  # existing error path

# Add an explicit guard for the unexpected case
analysis_result = state.get("analysis_result", "")
if not analysis_result:
    return {
        "final_output": {
            "frontline": [],
            "reserve": [],
            "synergy_explanation": "",
            "error": "No analysis result available — pipeline state inconsistency",
        }
    }
```

### WR-04: SSE `result` swap uses both `sse-swap` and `hx-target` on the same element — `hx-target` is ignored by the SSE extension and creates a misleading contract

**File:** `src/web/templates/partials/progress.html:18-22`
**Issue:** The `#result-area` div has both `sse-swap="result"` and `hx-target="#result-container"`. The HTMX SSE extension handles `sse-swap` events by swapping the content of the element bearing `sse-swap` directly — it does not respect `hx-target` for SSE-driven swaps. The `hx-target="#result-container"` attribute is therefore silently ignored. If a developer later expects `hx-target` to redirect the swap to `#result-container`, the result will not appear there, producing a hard-to-debug rendering failure.

Additionally, `#result-container` does not appear to exist in the rendered `progress.html` partial itself; it presumably exists in a parent template. If the parent template does not include a `#result-container` element, the `hx-target` attribute will silently fail. The `outerHTML` swap mode combined with SSE further complicates the element reference after the first swap.

**Fix:** Remove the non-functional `hx-target` and `hx-swap` attributes from `#result-area`. If the intent is to update an element outside `#result-area`, use the HTMX SSE `hx-swap` swap spec on the parent, or handle the DOM update in the `htmx:sseMessage` JavaScript handler (already present in the file for `node_status`).

```html
<!-- Remove hx-swap and hx-target — SSE extension ignores hx-target -->
<div id="result-area"
     sse-swap="result">
</div>
```

# Both roles use Nemotron on OpenRouter (no Haiku equivalent available)
